# Edwyz WA security review

Scope: `src/lib`, `src/app/api`, `src/app/webhooks`, `src/app/(auth)`, `src/app/(site)/oauth`, `src/worker`, `prisma/schema.prisma`, `deploy/nginx-wa.edwyz.com.conf`, plus a skim of `(app)` and `(admin)`. Method: paper review of the code at commit 3ee79bf plus the uncommitted working tree. Nothing was run, built or sent over the network. Line numbers refer to the files as read on 2026-10-26.

Correction to the brief: `src/lib/auth/csrf.ts:8-15` already rejects requests with NO Origin header. The permissive "no Origin passes" variant is only `src/lib/inbox/http.ts:5-9` (see F13). The bigger CSRF problem is that thirteen mutating handlers have no origin check at all (F2).

Severity scale: Critical = cross-tenant or platform-wide compromise with little effort. High = serious abuse or a gap Meta reviewers would flag. Medium = real weakness needing a precondition, or compliance or integrity damage. Low = hardening.

## Answers to the specific questions in the brief

1. **Tenant isolation.** Every Prisma query on tenant-owned models reachable from a route handler is scoped by `actor.tenantId` or by an id read through a scoped query. I found no read or write that crosses tenants and no id from the body used unscoped. templateId, phoneNumberId, contactId and conversationId are all re-fetched with `tenantId` in `broadcasts/service.ts:19-22`, `inbox/service.ts:138-141` and `inbox/service.ts:47-49`. The two checks that would catch a mixed-tenant pair (template WABA vs phone WABA at `broadcasts/service.ts:26`) are present. BroadcastRecipient and Message updates by wamid carry `tenantId` (`processor.ts:176,193`). Raw SQL exists only in `queue.ts:20-27` and is parameterised. The remaining risk is structural, covered by F13 and F16.
2. **Webhook cross-tenant writes.** The signature uses one app-wide secret, so it proves "sent by Meta", not "meant for this tenant". Routing then trusts `metadata.phone_number_id` (messages and statuses) and `entry.id` (template events). Nobody but Meta (or someone holding `META_APP_SECRET`) can produce a valid body, and a tenant cannot influence those ids, so I found no way to write into another tenant without the app secret. If that secret leaks, any tenant's inbox can be written to. Consider also checking that `entry.id` equals the resolved phone's WABA in `processMessagesChange` (`processor.ts:77-79`) as a cheap consistency check.
3. **Role escalation.** Not possible through the API. Invites cannot create owners (`invites/route.ts:12,37`), admin invites need an owner (`:38`), role changes require owner (`members/[userId]/route.ts:21`), admins cannot remove admins or owners (`:48-50`), and the role in the JWT is ignored because membership is re-read on every call (`auth/index.ts:12-21`). Agents can call all inbox and contact routes and read all conversations; admin-only routes use `requireRole` consistently, except that contact create/update is open to agents (F9).
4. **JWT.** HS256, signature compared with `timingSafeEqual` before parsing, `alg` checked, expiry enforced, no `none` path. Only weakness is secret strength and revocation (F21).
5. **Refresh rotation.** Single use, claimed atomically with `updateMany ... revokedAt: null` (`tokens.ts:89`), reuse revokes all sessions. Sound apart from the parallel-refresh logout in F21.

## Row-level security design (minimal, concrete)

Goal: a missing `where tenantId` can no longer leak data, without rewriting the app.

1. **Two database roles.** `edwyz_owner` runs migrations and owns the tables. `edwyz_app` (no `BYPASSRLS`, not owner) is used by the web process. A second role `edwyz_system` with `BYPASSRLS` is used only by the worker/webhook path and by auth lookups that have no tenant yet (login by email, refresh, invite lookup, webhook routing by `phone_number_id`).
2. **Tenant context per transaction.** Add `src/lib/db-tenant.ts` exporting `withTenant(tenantId, fn)`: it runs `prisma.$transaction(async (tx) => { await tx.$executeRaw\`select set_config('app.tenant_id', ${tenantId}, true)\`; return fn(tx); })`. `set_config(..., true)` is transaction-local, so it cannot leak across pooled connections. Route handlers call `withTenant(actor.tenantId, tx => service(tx, ...))`; services take a `tx` parameter instead of importing the global client. Do it for the inbox, contacts, broadcasts and templates modules first, then the rest.
3. **Policies.** For each table with `tenantId` (`Invite, Waba, PhoneNumber, AccessToken, OnboardingLog, Contact, Conversation, Message, Note, QuickReply, Template, Broadcast, BroadcastRecipient, WalletTransaction, AuditLog`, plus `Membership`, `Session` and `WebhookEvent` where `tenantId` is nullable):

```sql
ALTER TABLE "Contact" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "Contact" FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "Contact"
  USING ("tenantId" = current_setting('app.tenant_id', true))
  WITH CHECK ("tenantId" = current_setting('app.tenant_id', true));
GRANT SELECT, INSERT, UPDATE, DELETE ON "Contact" TO edwyz_app;
```

   If `app.tenant_id` is unset, `current_setting(..., true)` is NULL, the comparison is NULL and no rows match, so the failure mode is "empty result", not "everything". Tenant table itself: `USING (id = current_setting('app.tenant_id', true))`.
4. **Extra hardening.** `AuditLog`: grant INSERT and SELECT only. `AccessToken`: grant to `edwyz_app` only through a `SECURITY DEFINER` function used by `getAccessToken`, so a SQL injection or logic bug in a route cannot dump tokens. Add composite uniques `(tenantId, id)` on `Contact`, `Conversation`, `Template`, `PhoneNumber`, `Broadcast` and composite foreign keys from children (`Conversation(tenantId, contactId)`, `Message(tenantId, conversationId)`, `BroadcastRecipient(tenantId, broadcastId)` and so on) so a row can never point at another tenant's parent.
5. **System paths.** The worker, `processWebhookEvent`, `runDueJobs` and `auth/*` use a second `PrismaClient` bound to `edwyz_system`. Inside the worker, per-tenant work (`processSendJob`, `sendOne`) should still call `withTenant` so RLS applies to the writes.
6. **Rollout and test.** Add a vitest/integration test that connects as `edwyz_app`, sets tenant A and asserts a `select * from "Contact"` returns zero rows of tenant B, and asserts that with no context it returns zero rows. Roll out table by table; `FORCE` makes it apply to the table owner too, so migrations must run as `edwyz_owner` with `BYPASSRLS` or `SET row_security = off`.

## Checked and found sound

- Webhook POST: HMAC-SHA256 over the exact raw text body, `sha256=` prefix required, constant-time compare (`meta.ts:11-15`), rejected before JSON parsing, body size checked (nginx also limits to 4 MB). GET handshake compares the verify token in constant time and is disabled when the token is unset (`meta.ts:20-26`).
- Webhook processing is idempotent for messages (`wamid` unique plus P2002 handling) and for statuses (rank check), and an unknown phone or WABA is ignored with a note rather than created.
- Data-deletion signed_request: HMAC verified in constant time before parsing; the code returned is random (9 bytes); the status page validates the code with a strict regex.
- Password handling: per-user random 16-byte salt, constant-time verify, dummy hash on unknown email so timing does not reveal accounts, password length bounded at 200 on hashing.
- Refresh tokens and invite tokens: 256-bit random, only SHA-256 hashes stored, invites single use via an atomic `updateMany` claim (`accept-invite/route.ts:61-64`), expiry enforced.
- Session and workspace handling: membership re-read on every request; removal and demotion take effect immediately; `switch-workspace` verifies membership; no tenant id is ever trusted from a body or URL (the `tenantId` in switch-workspace is checked against membership).
- Onboarding: ids are validated as digits, ownership of the WABA and number is verified against the business token before anything is stored (`verifyIds`), already-owned numbers are rejected, PIN generated with `randomInt` and stored encrypted, excluded from `getAccessToken` (`crypto/tokens.ts:56-67`). The oauth callback page does not exchange or store anything and never chooses a tenant from the URL.
- Crypto basics: AES-256-GCM with a fresh random IV per encryption, key length enforced at 32 bytes, decrypt errors do not leak details (see F20 for the hardening items).
- No SSRF: the server never fetches a user-supplied URL; media links are forwarded to Meta as `link` and `https` is enforced in the route (`messages/route.ts:25`). Graph paths are built only from digit ids stored in the database, and `new URL` is anchored to `graph.facebook.com`.
- No SQL injection: the only raw SQL (`queue.ts:20-27`) uses tagged-template parameters; all else is Prisma.
- No ReDoS: regexes (email, template name, variables, phone) are linear and run on length-bounded input. No export route exists, so CSV formula injection does not apply today (when one is added, prefix cells starting with `= + - @ tab CR` with `'`).
- Mass assignment: routes pick named fields; Prisma `data` is never built from `...body`.
- Client side: no `dangerouslySetInnerHTML`, no tokens in `localStorage` or `sessionStorage`; auth cookies are `HttpOnly`.
- 24-hour window and template-only rule are enforced at queue time (`inbox/service.ts:99-103`); broadcasts require an approved template, an opted-in and not opted-out contact (checked again per send), and the tier throttle is applied.
- Redirects: only fixed paths (`/login?next=/app`); the `next` parameter is not consumed, so no open redirect.
